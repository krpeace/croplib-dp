# 0017. 적산온도는 운영 지점 전부, 물 수집은 수집 지점만 (#33 후속)

날짜: 2026-10-29

## 배경
- 10/28 지점 사전이 105곳(운영 97 + 폐지·휴지 8)으로 늘었다(CropMon#38). #33은 **감시**만 수집 지점(`has_forecast`)으로 좁혔고, 수집기 두 개는 아직 사전 전체를 돌았다.
- 적산온도(`heat-sun`)는 지점마다 지난 10년 + 올해를 해마다 받아(약 11번 × 105곳) 10/29 실행이 50분·56분 걸렸다(이전 약 5분). 작업 제한이 60분이라 조금만 느려져도 시간 초과이고, 실패 뒤 "5분 뒤 한 번 더"도 제한 안에 못 들어간다.
- 물 수집은 예보 없는 95곳도 회차마다 어제 ASOS를 받아 `weather_daily`에 썼다. 호출이 회차마다 95번 늘고 실행 요약이 넘쳤다.
- **사용자 결정(2026-10-29):** 적산온도·적산일사는 지도 사용으로 **전 지점** 공개한다. 물 계산 전 지점 확대는 그대로 #28에서 한다.

## 결정
### 대상 지점 기준 (열 하나씩, 일에 따라 다르다)
| 하는 일 | 대상 | 이유 |
|---|---|---|
| 적산온도·적산일사 수집 (`collectors/heat_sun.py`) | `is_active = true` 전부(지금 97곳) | 전 지점 공개. 폐지·휴지 8곳은 올해 관측이 없어 낼 수 없으므로 돌지도, 실패로 남기지도 않음 |
| 적산온도 감시 (`heat` 경고) | 위와 같음(운영 지점) | 수집 대상과 감시 대상을 맞춤 |
| 물 수집 (`collectors/water.py`, `--stations` 없을 때) | `has_forecast = true` 지점(지금 10곳) | 감시·`slot_done`과 같은 기준 |
| ASOS 관측 감시 (`asos` 경고) | `has_forecast` 지점 | 지금처럼. 경고 규칙은 안 바뀜 |
- `--stations`를 주면 두 수집기 모두 그 지점만 돈다(시험용, 폐지 지점도 가능).
- #28(물 계산 전 지점 확대) 때는 지점의 `has_forecast`만 켜면 수집·감시가 함께 따라간다(결정 0007 보충과 같은 원칙).
- 10/29 02시부터 이미 쌓인 95곳의 `weather_daily` 줄은 그대로 둔다(지우지 않음). 지우기가 필요하면 별도 이슈.

### 적산온도: 지난 해 원자료는 캐시하고 매일은 올해만 받는다
- 지난 해(올해 이전) ASOS 일자료는 바뀌지 않으므로 파일로 남긴다. `--cache-dir <폴더>`(기본 없음 = 예전처럼 다 받기), 파일은 `<폴더>/asos/<지점>/<해>.json`(`io/asos_cache.py`). **계산에 쓰는 5칸(`tm`, `avgTa`, `maxTa`, `minTa`, `sumGsr`)만 남긴다.** ASOS 응답은 한 줄에 칸이 60개 가까이라 그대로 두면 97곳 × 10해로 압축 전 수백 MB가 되고, 실행마다 새 키로 저장하는 캐시가 GitHub 한도(10GB)를 빨리 채운다. 5칸만 남기면 결과는 같고 크기는 약 1/10이다(처음 지시서의 "받은 items 그대로"를 바꿈).
- 캐시에 있는 해는 읽고 없는 해만 받는다. **올해는 항상 새로 받는다.** 받은 지난 해는 캐시에 쓴다. **다 받은 해만** 쓴다: 마지막 날짜가 12/31이거나 그해 관측이 아예 없을 때(nodata)만. 끝내 못 받은 해(실패)와 12/31이 빠진 해는 쓰지 않아 다음 실행에서 다시 받는다.
- 그해 관측이 없는 경우(`nodata`)도 빈 목록으로 캐시한다(다시 묻지 않게). 빈 목록과 "캐시 없음"은 다르게 다룬다.
- 캐시 파일이 깨져 있으면(JSON 오류 등) 그 해만 다시 받는다. 쓰기에 실패해도(임시 파일 정리 실패까지) 오류 없이 넘어간다. **캐시 때문에 실패하지 않는다.**
- 결과 계산(평년 = 지난 10년, 기준온도, `heat_daily`·`sun_daily` 덮어쓰기)은 바꾸지 않았다. 캐시를 쓴 결과와 다 받은 결과가 같은 것을 시험으로 확인한다.
- 실행 요약에 "ASOS 캐시: 읽음 N해 · 새로 받아 남김 M해"가 나온다(캐시가 실제로 쓰였는지 보기 위해).

### 워크플로(`heat-sun.yml`)
- GitHub `actions/cache`로 `.cache`를 저장·복원한다. **키 `asos-past-v1-${{ github.run_id }}`, 복원 후보 `asos-past-v1-`** — 매번 새 키로 저장하고 가장 최근 것을 복원한다. 해가 바뀌어도 겹치는 9년은 그대로 쓰고 새 해 1년치만 받는다.
- 복원(`actions/cache/restore`)과 저장(`actions/cache/save`, `if: always()`)을 나눠 썼다. 합친 `actions/cache`는 실행이 실패하면 저장하지 않는데, 캐시가 빈 첫 실행이 중간에 실패해도 받은 해는 남겨야 다음 실행이 이어 받는다.
- `timeout-minutes` 60 → 120 (캐시가 비었을 때 전체 받기 대비). **캐시가 있으면 목표 15분 이내.** "실패하면 5분 뒤 한 번 더"는 그대로 둔다(캐시가 있으면 두 번째도 짧다).
- 캐시 키 버전(`v1`)을 올리면 캐시를 새로 시작한다. 캐시 파일 모양을 바꾸거나, 지난 해 자료가 고쳐졌을 때 쓴다.

### 감시 보강 (`core/monitor.py`, `collectors/monitor.py`)
- **수집 지점 0곳 방어:** `has_forecast` 지점이 0곳이면 오류(`error:stale`급) "수집 지점이 0곳 — 지점 사전 has_forecast 확인". 전에는 0곳이면 관측·적산온도 경고가 조용히 사라졌다. 적산온도 대상(`is_active`)이 0곳일 때도 같은 이유로 오류를 낸다.
- **적산온도는 한 번에 묻는다:** `heat_daily?select=stn_id&date=eq.<어제>&crop_id=eq.common&gdd_cum=not.is.null` 한 번 → 운영 지점 목록과 비교해 빠진 지점을 경고. 매시간 호출은 회차 1 + 지점 2 + 관측 10 + 적산온도 1 = 14번(예전에는 지점 10곳 × 2).
- 빠진 지점이 10곳을 넘으면 "N곳 — 앞 10곳 …"으로 줄인다. 경고 열쇠는 "어제(날짜) 적산온도 없음"까지라서 빠진 지점 수가 달라져도 같은 경고로 본다(메일이 쌓이지 않음).
- 경고 규칙(13시간 멈춤·실패·지연·18시·12시)은 바꾸지 않았다.

## 알아 둘 것
- 새해 첫날 실행에서 지난 해 12/31 관측이 아직 안 올라왔어도 그 해는 캐시하지 않으므로, 빠진 채 10년간 평년에 쓰이지 않는다. 이미 잘못 남은 캐시가 있으면 키 버전(`v1`)을 올려 비운다.
- 캐시 크기는 첫 실행 뒤 Actions 화면의 캐시 목록에서 확인한다(97곳 × 10해, 5칸만 저장). 저장소 캐시 한도(10GB)·7일 미사용 만료 안에서 쓴다. 하루 최소 2번 새 키로 저장하므로 오래된 것은 GitHub가 알아서 지운다.
- 실행 화면 알림(annotation)은 약 4KB에서 잘린다. 적산온도 요약은 지점마다 한 줄이라 97곳이면 뒷부분이 잘릴 수 있다(전체는 실행 요약 화면과 결과 파일 `brief.md`에 있음). 필요해지면 별도 이슈로 줄인다.
