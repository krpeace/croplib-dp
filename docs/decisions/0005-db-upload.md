# 0005. DB에 올리기 (물3)

날짜: 2026-10-24

## 결정
- **올리기 전에 계약 검사를 한다** (`io/contract.py`, 데이터 계약 v1.2). 열 이름이 계약과 똑같은지, 비면 안 되는 칸, 값 범위, 정해진 이름(상태 코드·회차 결과·수집 방식), 키 중복을 본다. 범위는 계약서 값을 따르고, 계약서에 없는 칸은 물리적으로 말이 되는 넓은 범위를 정했다(풍속 0~60 m/s, ETc 0~25 mm, 심층침투 0~1,000 mm). 부족한 물(Dr)은 계산 조건마다 0~TAW.
- **한 줄이라도 어긋나면 그 회차의 계산 결과는 올리지 않는다.** 회차 기록(`forecast_runs`)은 "실패"와 첫 번째 이유를 담아 올려서 화면·수집 감시가 알 수 있게 한다. 종료 코드 1로 GitHub Actions 실행도 실패로 보인다. (CLAUDE.md: 어긋나면 올리지 않고 알린다)
- **덮어쓰기(upsert)로 쓴다.** 키(계약서)가 같은 줄은 새 값으로 바뀐다. 회차마다 작기 전체의 관측 물수지를 다시 계산하므로(Kc 기후보정이 작기 진행에 따라 바뀜) 지난 날의 값도 고쳐진다. 같은 회차를 다시 돌려도 줄이 늘지 않는다. 회차 기록도 마지막 실행으로 바뀐다(물2의 재시도는 실패한 회차만 다시 돌림).
- **3일 전망은 회차 번호(`run_id`)를 받아 붙인다.** `forecast_runs`를 먼저 쓰고 돌려받은 번호를 (발표 시각, 지점, 수집 방식)으로 찾아 `water_outlook`에 넣는다.
- **예보 원자료만 Storage에 보관한다.** 단기예보 API는 지난 하루치 발표만 주므로 나중에 다시 받을 수 없다. 발표마다 한 파일(`raw/fcst/<격자>/<연>/<월>/<발표>.json.gz`, 여러 쪽을 한 파일에)로 두고 다시 받으면 덮어쓴다. 춘천 한 곳이면 하루 8개 발표 × 약 15~20 KB로 한 해 수십 MB다. ASOS는 언제든 다시 받을 수 있어 보관하지 않는다.
- **원자료 올리기가 실패해도 계산 결과는 올린다.** 문제로 남기고(종료 코드 1) 그 회차의 `raw_path`는 비운다. 계산 결과가 화면에 더 중요하기 때문이다. 표 쓰기가 실패하면 바로 멈추고 오류를 낸다.
