# 0022. 전망 표 월 보관·삭제·복원, 대표 밖 예보 원문 90일 규칙 (#61, #28 S3-a)

날짜: 2026-11-08 (계획 승인 #61, 구현 S3-a. 용량 경고는 S3-b)

## 배경
- DB 무료 500MB(실측 57MB, 확정안은 2028년 말~2029년 초에 한도, #28 2-4절). `water_outlook`·`water_outlook_summary`는 지우는 코드가 없어 대표 10곳만으로 연 약 43MB, 97곳이면 연 약 192MB씩 늘어난다.
- 화면(CropMon)은 지점당 최근 4회차·전체 최근 40회차(이틀)의 `run_id`로만 전망을 읽는다(CropMon 코드 확인). 14일보다 오래된 전망 줄은 화면이 읽지 않는다.
- 두 표의 `run_id`는 `forecast_runs.run_id`를 가리키는 외래키다. `forecast_runs`를 지우지 않으면 보관 파일로 되살릴 때 `run_id`가 계속 유효하다.
- 승인: #28 D3·D4(2026-11-07), #61 Q1~Q5(2026-11-08).

## 결정
1. **보관 대상:** `forecast_runs.run_at`의 **한국 날짜가 오늘 − 14일보다 앞인** `water_outlook`·`water_outlook_summary` 줄. 오늘 − 14일부터는 DB에 남긴다(오늘 11/8이면 10/25부터 남김, 10/24까지 대상). `forecast_runs`·`weather_daily` 등 다른 표는 지우지 않는다.
2. **보관 파일 경로·이름:** `raw` 버킷(계약 v1.2) 안 `archive/` 아래, 새 버킷은 만들지 않는다.
   - `archive/water_outlook/<연>/water_outlook_<연>-<월>.csv.gz` 예: `archive/water_outlook/2026/water_outlook_2026-10.csv.gz`
   - `archive/water_outlook_summary/<연>/water_outlook_summary_<연>-<월>.csv.gz`
   - 월은 `run_at`의 **한국 날짜** 기준(한국 11/1 01:00 회차는 11월 파일).
3. **보관 파일 내용:** UTF-8 csv, 첫 줄 열 이름. **앞 4열 `run_at, run_name, stn_id, collector`(forecast_runs에서) + 표의 모든 열(`run_id` 포함)**. `run_at`은 한국 시각(`2026-10-20T17:00:00+09:00`)으로 통일한다. 빈 칸은 `null`. 줄 순서 `run_at, stn_id, scenario_id, target_date`. gzip은 `mtime=0`이라 같은 내용은 같은 파일(sha256)이다. `run_name`(아침/저녁)을 계획서보다 더 넣어, 파일만 봐도 어느 회차인지 알고 오차표 재집계에 쓸 수 있다.
4. **월 파일 합치기:** 그 달 회차가 지워질 때마다 기존 파일을 내려받아 새 줄을 더하고(키 `(run_id, scenario_id, target_date)` / `(run_id, scenario_id)`가 같으면 한 줄) 다시 올린다. 같은 작업을 두 번 해도 결과가 같다. 기존 파일이 깨져 읽히지 않으면 덮어쓰지 않고 멈춘다.
5. **삭제 전 확인(모두 통과해야 지움, 하나라도 어긋나면 그 뒤를 하지 않고 멈춤):**
   1. 보관 파일을 올린 뒤 **다시 내려받아** 올리기 전 계산값과 sha256이 같다.
   2. 내려받은 파일의 줄 수가 올리기 전 계산값과 같다.
   3. **지울 줄의 키가 모두 파일에 있다.**
   4. 지우기 직전에 그 회차 묶음(50회차)의 줄을 다시 읽어, **보관 파일에 없는 줄이 하나라도 있으면(보관 뒤 늦게 생긴 줄) 지우지 않고 멈춘다.**
   5. 지운 줄 수가 읽은 줄 수와 같다.
6. **승인 절차(실제 삭제는 PR 병합 뒤 사용자가 승인할 때 수동 실행 한 번):**
   - 기본은 읽기만 하는 **dry-run**(`plan`). 지울 줄 수(표별)·회차 수·월별 보관 파일(새 줄·기존 줄·합친 줄·csv/gz 크기·경로·sha256)·삭제 전후 줄 수·줄어드는 DB 용량·`forecast_runs` 줄 수(삭제 0)·Storage 사용량·xz로 바꾸면 줄어드는 크기를 보고한다.
   - 실제 삭제(`apply`)는 **`--through <날짜>`와 `--confirm-rows <N>`을 모두 줘야** 한다. N은 dry-run이 보고한 "그 날짜까지의 지울 줄 합계"다. 다르면 아무것도 지우지 않고 멈춘다. 날짜를 고정하므로 승인과 실행 사이에 새로 14일을 넘긴 줄이 끼어도 영향이 없다. `--through`는 오늘 − 15일보다 늦을 수 없다(14일 안의 줄을 지울 수 없음).
   - 워크플로 `retention.yml`은 예약 없이 사람이 눌러야 돈다(서버 키 사용).
7. **`forecast_runs`는 지우지 않는다**(전량 보관). 코드에 이 표를 지우는 호출이 없다(시험으로 확인). 수정은 하나뿐이다: 지운 원문 파일을 가리키던 `raw_path`를 비운다(줄은 그대로).
8. **예보 원문 Storage 보관 기간:**
   - 대표 10곳(`fcst/<격자>/<연>/<월>/<발표>.json.gz`)은 지금처럼 보관한다. **이름 규칙상 정리 대상이 아니다**(`fcst-ext/`로 시작하지 않는 경로는 어떤 경우에도 대상이 아님, 시험으로 확인).
   - 대표 밖 지점 원문은 **`fcst-ext/<격자>/<연>/<월>/<발표>.json.gz`** 에 둔다(경로 함수 `core/retention.raw_path`·`raw_prefix`, 쓰는 것은 S4). 파일 이름의 **발표 시각이 90일(정확히 90일은 남김, 91일부터)** 지난 것만 지운다. 지울 때 `forecast_runs.raw_path`가 그 경로인 줄은 `raw_path`만 비운다. 같은 승인 절차(dry-run → `--confirm-raw-files <N>`, 줄 수 확인과 함께).
   - 지금은 대표 밖 예보가 없어 **실제 삭제 대상은 0건**이다(규칙과 시험만).
   - "대표"의 정의(지금 `has_forecast` 10곳)는 S4가 `has_forecast`를 더 켜기 전에 고정된 목록으로 정해야 한다(열린 항목, S4).
9. **예보 원문의 압축:** 지금 Storage 원문은 **이미 gzip**이다(`ForecastCollector.raw_files()`, 평균 4,542B, 풀면 152KB, 압축률 3.0%, 2026-11-08 실측 199개). xz(9e)로 바꾸면 gzip의 50.9%(2,314B)다. **쓰는 형식 변경은 이 PR에 넣지 않았다**(기존 시험 `tests/test_upload.py`의 경로 확장자·압축 해제 기대값을 바꿔야 해서 사용자 승인이 필요, #61 Q6). 대신 `core/retention.read_raw_doc()`이 gzip·xz를 매직 바이트로 알아보고(시험), dry-run이 "xz로 바꾸면 줄어드는 크기"를 표본(기본 200개)으로 보고한다. **기존 원문을 압축본으로 바꾸는 일은 삭제를 동반하므로 하지 않는다.**
10. **조인 조회 대비:** 보관 대상 줄은 `forecast_runs!inner(...)` 외래키 조인으로 한 번에 읽는다. 조인이 안 되는 응답(HTTP 400·PGRST200)이면 회차를 먼저 읽고 줄을 `run_id` 묶음으로 따로 읽어 같은 결과를 낸다(시험). 다른 오류는 숨기지 않고 멈춘다.

## 복원 절차
보관 파일에서 표로 되살리는 방법은 두 가지다.
1. **`restore`(권장):** `python -m croplib_dp.collectors.retention restore --table water_outlook --month 2026-10`(워크플로 `retention` → `mode=restore`). 기본은 **보고만** 한다: 파일의 줄 수, 모든 `run_id`가 `forecast_runs`에 있는지. `--apply`(워크플로 `restore_apply` 켬)를 주면 같은 키로 **`upsert`** 한다(없던 줄은 생기고 있던 줄은 같은 값). `forecast_runs`에 없는 `run_id`가 하나라도 있으면 복원하지 않고 멈춘다(외래키).
2. **손으로:** 보관 파일은 CSV라서 앞 4열(`run_at, run_name, stn_id, collector`)을 빼면 DB 열과 같다. 대시보드 Table Editor의 CSV 가져오기로도 되살릴 수 있다.
- **주의:** 복원한 줄이 14일을 넘었으면 다음 보관 실행이 다시 보관 파일로 옮기고 지운다(합치기는 중복을 한 줄로 하므로 파일은 그대로다). 복원은 분석·화면 확인용으로 쓰고, 오래 두려면 보관 실행의 `--through`를 조정한다.
- 첫 실제 삭제 전에 **복원 dry-run**(`mode=restore`, 보고만)으로 보관 파일이 읽히는지 사용자가 확인한다.

## 보관 파일로 예보 검증(오차표 재작성)을 할 수 있나
- 오차표(`fcst_error_table.csv`)는 **발표된 예보 ETo와 관측 ETo의 비교**다(cropwater `cum3` = 발표별 처음 3개 대상일 ETo 합의 오차).
- **쓸 수 있다:** 보관 파일에 `run_at, run_name, stn_id, target_date, lead_day, eto_mm`가 있고 관측 `weather_daily.eto_mm`가 전량 보관되므로, 게시된 예보의 발표·선행일·월별 오차(n, RMSE, MBE, 관측 평균)와 `cum3`를 다시 집계할 수 있다(같은 지점의 ETo는 시나리오와 무관하니 지점·날짜당 한 줄). 작물 의존 오차(ETc)는 `etc_mm`·`etc_sum_mm`을 관측 `water_balance_daily`와 붙인다. 시험(`test_archive_can_rebuild_cum3_forecast_error_with_observed_eto`)이 이 변환을 확인한다. 지속(persistence) 비교 기준은 보관 파일에 없지만 `weather_daily`의 직전 관측 ETo로 다시 만들 수 있다.
- **쓸 수 없다:** 일사 추정 방식을 바꿔 **예보를 다시 계산**하는 검증은 시각별 원문이 필요하다. 대표 10곳은 `fcst/`에 계속 보관되고 대표 밖은 90일이다.

## 알아 둘 것·한계
- **줄당 크기 실측:** 보관 csv.gz는 줄당 8.7B(water_outlook)·7.0B(summary)(최근 5회차 1,250줄). 1년 예상은 지금 약 1.6MB, 2단계 이후 약 7.4MB(계획서의 연 31MB는 40B 가정이라 과대였다). dry-run이 실제 크기를 보고한다.
- **첫 실제 삭제 규모:** 지금은 10/24부터 쌓여 하루치(약 500줄, 약 0.1MB)뿐이다. DB 용량 효과는 시간이 갈수록 커진다.
- **조인 조회**는 이 저장소 시험(가짜 DB)에서만 확인했다. 실제 DB 응답 형식은 첫 dry-run이 확인한다.
- 서버 키(삭제 권한)를 쓰는 워크플로가 하나 늘어난다. 사람이 눌러야만 돌고 키는 환경변수로만 읽는다.
- DB 구조·`CALC_VERSION`·계약 버전 변화 없음.

# S3-b: 용량 경고와 주간 정기 실행 (#61, 2026-11-08)

## 결정
1. **DB 용량 경고(수집 감시, 매시):** 정확한 값은 **400MB 경고 / 450MB 오류**, 정확한 크기를 읽기 전의 **추정은 360MB 경고 / 405MB 오류**(오차 ±10% 여유). 한도는 500MB. 경고 열쇠는 문구 앞부분(`DB 용량 경고선 초과`)이라 숫자가 바뀌어도 같은 경고로 보고 이슈에 댓글이 쌓이지 않는다. 오류선으로 올라가면 새 경고로 댓글이 달린다. 크기를 못 읽으면 `DB 용량 조회 실패` 경고(조용히 넘어가지 않음).
2. **크기 읽기:** CropMon 함수 `public.db_size_bytes()`([CropMon#77](https://github.com/krpeace/CropMon/issues/77))를 먼저 부르고(`POST /rest/v1/rpc/db_size_bytes`, 응답 `{db_bytes, tables}`), 함수가 없거나(404) 이 키로 부를 수 없으면(401·403) **표 8개의 줄 수 × 줄당 실측 크기 + 시스템 영역 12MB + 작은 표 1MB**로 추정한다(`heat_daily` 219B, `soil_water_daily` 253B, `sun_daily` 187B, `water_balance_daily` 376B, `water_outlook` 247B, `weather_daily` 301B, `water_outlook_summary` 245B, `forecast_runs` 224B 추정). E2 줄 수(2026-11-08)로 계산하면 실측 57MB와 맞는다(시험). 그 밖의 오류(HTTP 500 등)와 엉뚱한 응답은 추정으로 덮지 않고 조회 실패로 알린다. 함수가 생기면 코드 수정 없이 자동으로 정확한 값으로 바뀐다.
3. **egress 영향:** 줄 수는 `HEAD`가 아니라 `GET` + `Prefer: count=exact` + `Range: 0-0`(한 줄만, 본문 거의 없음) 8번, RPC 1번이 매시간이다. 응답 본문이 몇 백 바이트라 하루 egress 약 0이다(Supabase egress 조사 #66과 충돌하지 않게 설계).
4. **Storage 용량 경고는 주 1회 정기 실행에서 확인한다(승인된 계획에서 바뀐 점):** 모든 버킷(`raw`, `krei-raw`)의 파일 크기 합이 **800MB 경고 / 950MB 오류**(한도 1GB 가정, 실제 한도가 확인되면 상수만 고침). 매시 감시에서 하지 않는 이유: ① Storage에는 전체 크기를 주는 호출이 없어 폴더마다 목록을 읽어야 하는데 파일 항목당 약 400B라 지금 약 13MB, 매시 하면 하루 300MB(#66 문제를 우리가 만드는 꼴), ② 감시 이슈는 "경고가 없으면 정상 회복으로 닫는" 방식이라 하루 한 번만 보면 나머지 시간에 경고가 닫혔다 열린다. 경고는 자기 이슈(`[용량·보관 경고] 저장 공간과 전망 표 보관`, 라벨 `용량 경고`)로 낸다. Storage 증가가 하루 약 0.4MB라 최대 일주일 늦은 알림은 문제가 없다.
5. **retention 주 1회 정기 실행:** `retention.yml`에 예약(매주 월요일 03:30 KST)을 더하고 모드 `weekly`를 만들었다. `keepalive.yml`의 다시 켜기 목록에도 넣었다.
   - **기본은 읽기만(plan) + 경고:** 보관 대기 줄 수(`--through` 포함)·Storage 용량을 보고하고, 대기 줄이 있으면 `보관 대기` 경고를 한 번 낸다(자동 삭제가 꺼져 있을 때의 알림, 한 이슈에 계속 두고 댓글을 쌓지 않음).
   - **자동 삭제는 사용자가 Actions 변수 `RETENTION_AUTO_APPLY=true`를 켰을 때만** 한다(첫 실제 삭제를 승인·확인한 뒤에 켜는 스위치, **기본 꺼짐**). 켜져 있어도 S3-a와 같은 확인을 모두 거친다: 보관 파일을 올린 뒤 다시 내려받아 sha256·줄 수 확인, 지울 줄이 모두 파일에 있음, 지우기 직전에 보관 파일에 없는 줄(늦게 생긴 줄)이 있으면 중단, `forecast_runs`는 지우지 않음. 어긋나면 지우지 않고 `보관·삭제 중단` 오류 경고(이슈 + 워크플로 실패).
   - **한 번에 지우는 상한 `--max-rows`(기본 8,000줄, 지금 주 약 3,500줄):** 넘으면 자동 삭제를 하지 않고 `자동 삭제 상한 초과` 오류 경고. 예상 밖으로 많이 쌓였다는 뜻이므로 dry-run을 보고 수동 `apply` 한다. S2·S4로 지점이 늘면(주 약 15,700줄) 이 상한을 함께 올린다.
   - 주간 점검의 모든 예외는 올리지 않고 `보관·삭제 중단` 오류 경고로 남기고 종료 코드 1로 끝낸다.
6. **자동 삭제를 켜는 순서(사용자):** ① S3-a·S3-b 병합 → ② `retention` `mode=plan` 확인 → ③ 승인한 `mode=apply` 첫 실행 → ④ GitHub 저장소 Settings → Secrets and variables → Actions → **Variables**에 `RETENTION_AUTO_APPLY` = `true` 추가. 끄려면 값을 지우거나 `false`.
7. **시험의 시간 의존 제거:** `collectors/retention.main()`에 `now` 인자를 더했다. S3-a의 CLI 시험 5개가 실제 시계(`kst_now()`)에 기대고 있어, 날짜가 지나면(14일 기준이 움직여 대상 줄 수가 16에서 늘어남) 내일부터 깨질 시험이었다. 고정 시각(`NOW`)을 넘기도록 호출만 고쳤고 기대값은 그대로다.

## 알아 둘 것·한계
- 추정은 줄당 크기가 실제와 다르면 틀린다. 그래서 경고를 일찍(360MB) 내고, CropMon#77이 생기면 정확한 값으로 바뀐다. 현재(약 57MB) 경고선까지 약 300MB 여유라 급하지 않다.
- Storage 한도 1GB는 가정이다(사용자가 대시보드에서 확인 예정). 합계가 800MB에 닿으려면 3년 안에는 어렵다(#28 1절 표).
- `RETENTION_AUTO_APPLY`를 켜기 전에는 매주 `보관 대기` 경고 이슈가 열려 있다(승인 전 알림 목적). 켜서 대기 줄이 0이 되면 "정상 회복"으로 닫힌다.
- GitHub 예약 실행은 늦거나 건너뛸 수 있다(주 1회라 영향이 작고, 건너뛰어도 다음 주에 한꺼번에 처리한다).
- 새 시험: `tests/test_db_size.py`(DB 크기 규칙·읽기 15개), `tests/test_retention_weekly.py`(주간 실행·Storage 경고·워크플로 설정 19개), `tests/test_retention.py`에 경고선·추정 4개.
