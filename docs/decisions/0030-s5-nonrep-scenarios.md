# 0030. 대표 밖 87곳 3일 전망·물수지 켜기 준비 (S5-a, #87)

날짜: 2026-11-10 (사용자 승인 #87 §8 답 + 추가 지시)

## 배경
S5는 CropMon이 계산 조건(사과 k3·배추 k1, 2026·2027 = 87 × 2 × 2 = 348행)을 시드한 **대표 밖 87곳**에 ① 3일 전망(`water_outlook`·`water_outlook_summary`)과 ② 2026 `water_balance_daily`를 만든다. 전망은 소급하지 않는다(2026 예보 원문 없음). 계획은 #87 댓글. 이 문서는 S5-a(코드, **스위치 기본 꺼짐**)의 결정이다.

## 결정 (사용자 확정)
1. **앞선 발표는 "필요한 것만"**(S4 결정 ④ 재결정): 대표 밖은 **02시 회차 3시간 전 + 24시간 전(어제 아침 발표), 17시 회차 3시간 전 + 15시간 전(오늘 아침 발표)**(`NONREP_CATCHUP_BACK`). 개수는 2개로 그대로라 호출·시간은 늘지 않는다. 대표 10곳은 24시간 안 8개 그대로.
   - 이유: 어제를 채우는 값은 "그날 아침 발표 D+0"이다(`core/outlook.py` `fill_from_forecast`·`day_forecast`). 02시 회차는 ASOS에 어제가 아직 없어(관측: 마지막 = D−2) 어제의 02시 발표가, 17시 회차는 저녁 발표 규칙상 오늘 02시 발표가 필요하다. S4의 "가장 최근 2개(3·6시간 전)"로는 둘 다 없어 **전망을 켜는 순간 전부 "진행할 예보가 없습니다"로 실패**한다(시험으로 고정).
   - 한계: ASOS가 이틀 이상 늦어 D−2 아침 발표가 필요한 날은 대표 10곳도 지금 실패한다(`CATCHUP_H` 24시간). 그 지점만 재실행되고 감시가 알린다.
   - **시드 뒤 소규모 dry-run으로 실제 예보 검증 단계를 꼭 넣는다**(아래 순서 3번): 코드 읽기와 가짜 발표 시험으로 정한 규칙이라 실제 예보로 확인한 뒤 켠다.
2. **스위치 = Actions 변수 `NONREP_SCENARIOS`**(기본 꺼짐, `true`일 때만 켜짐). 꺼져 있으면 시나리오가 시드돼 있어도 대표 밖 지점은 계산 조건을 **무시**한다(결정 0026 3번 방식). 시드와 켜기를 분리한다. 시험 실행(`dry_run`)에서만 새 수동 입력 `nonrep_scenarios`로 변수 없이도 대표 밖 전망을 계산해 볼 수 있다(DB에 쓰지 않음, 쓰는 실행에 주면 멈춤).
3. **14일 창을 대표 밖 전부로 넓히고 `water_balance_daily`까지**(결정 0026 12번 확장): 대표 밖 지점은 관측·예보·계산 조건 유무와 상관없이 `weather_daily`·`soil_water_daily`·`water_balance_daily` 모두 어제 포함 14일 창만 올린다. 계산은 작기 시작(3/1부터 받은 기상값 전체)부터 다시 하므로 **창 안 값은 전체와 같다**(시험). 대표 10곳은 그대로. 소급(`--soil-backfill`)은 창이 없다.
   - S4-b 후속(#94)의 창 조건은 "계산 조건이 없는 대표 밖"이었다. 그대로 두면 **시나리오를 시드하는 순간 `weather_daily`를 3/1~어제 전부(약 250줄 × 87곳) 다시 올리게 되므로** 조건에서 "계산 조건이 없는"을 뺐다.
4. **소급 = `--wb-backfill`**: 예보·전망·`forecast_runs` 없이 ASOS만 받아 그해 작기 시작~어제(ASOS가 있는 마지막 날)까지 `water_balance_daily`를 계산해 올린다(`run_wb_backfill`). **한 번에 대표 밖 20곳까지, 지점 번호 필수, 늘 `dry_run`(요약에 줄 수·예상 DB 증가 MB)이 먼저.** 정기 회차와 같은 날짜(3/1)부터 같은 계산을 하므로 값이 같다(시험). 쓰려면 변수 `NONREP_SCENARIOS`가 켜져 있어야 한다. ASOS가 실패한 지점이 있으면 문제로 남기고 쓰지 않는다. 어제가 아직 ASOS에 없으면 그날 줄은 정기 회차가 예보로 채운다.
5. **retention 주간 삭제 상한 20,000 → 40,000**(결정 0022 갱신). 아래 "상한 결정과 이유".
6. **켜는 날은 사용자가 정한다**: S4 완료 판정(11/11 02시 회차 뒤)과 S5-a 병합 뒤.

## 순서 고정: S5-a 병합 → CropMon 시드 → 변수 켜기 → 소급
- **S5-a 병합 전에 CropMon이 시나리오를 시드하면 안 된다**: 병합 전 코드(#94)의 14일 창은 "계산 조건이 없는" 대표 밖에만 걸려 있어서, 시드가 먼저 들어가면 대표 밖 87곳이 `weather_daily`를 회차마다 3/1~어제 전부 다시 올린다(S4-b에서 막은 문제가 되살아남).
- S5-a 병합 뒤에는 시드가 먼저 들어가도 안전하다(스위치가 꺼져 있으면 무시).
- 변수를 켠 뒤 첫 정기 2회차를 확인하고 소급(20·20·20·20·7곳, 매번 dry-run → 승인 → 쓰기)을 한다. 소급 값은 14일 창과 같은 계산이므로 앞부분(작기 시작~14일 전)만 채워진다.

## 상한 결정과 이유 — 40,000으로 올리고 "나눠 지우기"는 하지 않는다
사용자 요청: 주간 삭제 15,680줄이 상한 20,000의 78%라 한 주만 빠져도 멈추므로 ① 상한을 40,000으로 올리거나 ② 밀린 주를 나눠 지우게 하되 나은 쪽을 이유와 함께.
- **택한 것: ① 40,000.** 한 주를 건너뛰어도(31,360줄) 한 번에 처리되고(상한의 78%), 세 주 밀리면(47,040줄) 멈추고 사람이 본다.
- **② 나눠 지우기를 택하지 않은 이유**:
  1. **상한은 "예상 밖으로 많이 지우는 일"을 막는 안전장치**다. 상한을 넘으면 자동으로 일부만 지우도록 하면, 어떤 오류로 줄이 갑자기 늘거나 날짜 기준이 어긋나도 **사람이 보기 전에 조금씩 계속 지워진다.** 멈추고 알리는 것이 이 장치의 목적이다.
  2. 구현이 더 복잡하다: 부분 삭제는 `--through`와 `--confirm-rows`의 확인(계획한 줄 수 = 지운 줄 수)을 날짜 중간에서 끊어야 하고, 남은 양을 다음 주에 이어 받는 상태가 생긴다. 지우는 길에는 새 실패 방식을 더하지 않는다.
  3. 나눠 지워도 상한이 주간 유입(15,680)보다 작으면 밀린 양이 줄지 않는다(20,000이면 주 4,320줄씩만 줄어듦). 상한을 키우는 것이 더 단순하고 같은 효과다.
- 세 주 이상 밀리는 일은 자동 삭제가 꺼져 있거나(`RETENTION_AUTO_APPLY=false`) 실행이 계속 실패한 때라 사람이 봐야 하는 상황이다(보관 대기 경고·`자동 삭제 상한 초과` 오류 경고가 이미 있음).

## S5-a가 함께 고친 것
- **알림 요약(`brief.md`)이 예보 지점 97곳에서 4KB를 넘는다**: 대표 밖 예보 지점도 지점마다 한 줄이라(S4 c2 이후) 알림 칸(약 4KB)에서 뒤쪽 `DB 올리기` 줄까지 잘렸다. 이제 **대표 밖 예보 지점은 한 줄로 모으고 정시 성공이 아닌 지점만 이름을 적는다**(최대 10곳, 나머지는 "외 N곳"). 대표 10곳은 지점마다 한 줄 그대로. 소급 요약도 한 줄.
- **`단계:` 줄에 시나리오 수와 계산 시간**(`시나리오 N개 계산 …`): API 기다림을 뺀 계산 시간의 첫 실측 근거(S5 켠 뒤 회차 시간 +3~6분 추정을 확인한다).
- 켠 뒤 `forecast_runs.rs_method`가 null → `S3`로 바뀌는 것이 정상이다(대표 밖은 S4 계수가 없어 평소 방식이 S3).

1. **C6 시드**: 대표 밖 87곳 × (사과 k3, 배추 k1) × 2026·2027 = 348행(`scenarios`: `taw_mm`·`raw_mm`·`dr0_mm`·`season_start`·`soil_code` 포함). S5-a 병합 뒤 스위치가 꺼진 동안 실행해도 안전(무시됨).
2. "검증 전" 표시 확대, 대표 밖 "자료 없음" 안내 정리(C1), 대표 밖 전망이 화면에서 대표와 같은 방식으로 읽히는지 확인(전망 읽기가 지점별 최신 회차를 찾는지 — 판정 표 P7과 같은 종류).
