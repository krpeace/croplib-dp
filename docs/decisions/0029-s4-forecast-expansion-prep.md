# 0029. 예보 지점을 20곳씩 켜기 전 준비 (S4-a, #88 · #85 결정 ①~⑤)

날짜: 2026-11-09 (사용자 확정 #85 댓글)

## 배경
S4는 새 87곳을 `has_forecast = true`로 켜 예보 지점을 10곳 → 97곳으로 넓히는 일이다(켜는 `update`는 사용자가 SQL Editor에서 실행). 켜기 전에 이 저장소 코드가 지점 수 증가를 견디게 한다.

## 결정 (사용자 확정)
1. **켜기는 두 번**(S4-c1 #90, c2 #91): c1 = 1묶음 20곳(90~137) → 정기 2회차 확인 → c2 = 나머지 67곳 한 번에.
2. **대표 판별 = `stations.is_representative`**(`is_representative(st)`). 계산 조건으로 추정하지 않는다. 칸이 답에 없으면 대표로 본다(대표의 앞선 발표·원문을 줄이지 않는 안전한 쪽; 실제 DB는 칸이 있고 기본 거짓).
3. **재실행은 '정시 성공'이 아닌 예보 지점만 다시 돈다**(`pending_forecast_stations`). 지점 하나가 실패해도 예보 지점 전부를 다시 돌지 않는다. 아무 지점도 못 끝낸 회차는 지금처럼 전부 돈다. **관측만 하는 지점은 재실행에서도 다시 받는다**(약 4분 이내): 첫 시도에서 계약 검사 실패로 관측 줄이 못 올라간 경우까지 안전하게 메우려는 해석이다(사용자가 "관측도 건너뛰라"고 하면 한 줄로 바꾼다).
4. **대표 밖(`is_representative=false`) 예보 지점은 앞선 발표 8 → 2개**(`CATCHUP_NONREP_N`), 가장 최근 앞선 발표부터. 대표 10곳은 8개 그대로. 원문은 대표 밖만 **`fcst-ext/`(90일 보관) + 서비스 발표만**(대표는 `fcst/` 그대로, 받은 발표 전부). 앞선 발표를 대신 쓴 경우 `forecast_runs.raw_path`가 올리지 않은 파일을 가리키지 않게 비운다.
5. **retention 주간 자동 삭제 상한 8,000 → 20,000줄**(결정 0022 갱신). 전망 2표 주간 삭제량은 대표 밖 전망(S5)이 켜지면 약 15,700줄이다. S4 단독으로는 전망 표가 늘지 않으므로 지금은 안전 여유다.

## S4-a가 함께 고친 것
- **계산 조건이 없는 예보 지점이 '정시 성공'이 될 수 있게 했다.** 이전에는 일사 방식(`rs_method`)이 3일 전망 계산에서만 정해져서 전망을 만들지 않는 지점은 `rs_method`가 비어 '백업: S3'가 되었고, `slot_done`이 '정시 성공'만 완료로 보므로 **새 지점을 켜는 순간 회차가 영영 끝나지 않고 재실행**됐을 것이다(계산 조건이 있는 지점은 규칙 그대로). 기준: 서비스 발표를 정시에 다 받고 백업을 쓰지 않았으면 정시 성공.
- **감시가 `forecast_runs`를 최신 20줄이 아니라 최근 48시간 전부(쪽 나눠 읽음)로 읽는다**(P8). 한 회차가 지점 수만큼 줄을 만들므로 20곳이 넘으면 일부 지점을 못 본다. 예보를 할 수 있는 지점(`has_forecast` + DB 격자 있음)인데 최근 48시간 기록이 없으면 경고 `예보 지점 회차 기록 없음 … (켠 직후)`. 방금 켠 지점은 다음 회차까지 이 경고가 뜰 수 있어 **경고(오류 아님)이고 문구에 "켠 직후"를 적었다**. CropMon 판정 표의 40줄 한도는 CropMon P7(사용자가 요청함).
- **DB 크기 한 줄**: 감시가 매번 `DB 크기: 65.3MB (정확: db_size_bytes() 값) · 경고선 400MB·오류선 450MB`를 남긴다. 추정이면 `약 …MB (줄 수로 추정한 값 …) · 경고선 360MB·오류선 405MB`와 함께 **"정확한 값으로 읽지 못함" 경고**(조용히 추정으로 가지 않음). 읽기 실패면 `읽지 못함 — 이유`.
- **한 회차 단계별 시간·호출 수**를 요약·짧은 요약에 남긴다: `단계: 예보 지점 N곳 …분 …초 · 관측 지점 M곳 … · 예보 요청 a번(발표 단위, 쪽 수 제외) · ASOS b번`. c1·c2에서 처음 실측하는 값이다.
- **S6 번호 연결**: DB 용량 경고(`dbsize`)와 retention 용량 경고 이슈 본문에 "오래된 해 정리(S6, #86)"와 착수 조건(2027년 하반기 또는 DB 400MB 경고 중 먼저 오는 쪽)을 적는다.

## 알아 둘 것
- **앞선 발표를 2개로 줄인 것은 전망(S5)에서 다시 정해야 한다**: 지금 대표 밖 지점은 계산 조건이 없어 앞선 발표를 쓰지 않는다. S5에서 전망을 만들려면 앞선 발표로 어제 하루를 채우는 계산이 필요하고(11/9 안동 사례: 앞선 발표 1개를 못 받아 "진행할 예보가 없습니다"), 2개로는 모자랄 수 있다(#87에 적음).
- 재실행이 일부 지점만 돌 때 이미 정시 성공한 지점의 줄은 그대로 두고 실패 지점 줄만 새로 쓴다(`forecast_runs`는 같은 키로 덮어씀).
- 시간·호출 수 예상(#85 3절)은 대표 10곳 실측에서 뽑은 추정이다.

## 시험 (`tests/test_s4a.py`, 20개)
