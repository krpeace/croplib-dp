# 0004. 서버 수집기 (물1-3)

날짜: 2026-10-24

## 결정
- **회차마다 새로 받는다.** 서버(GitHub Actions)는 매번 빈 컴퓨터에서 시작한다. 현장 PC는 받은 예보를 폴더에 쌓지만, 서버는 회차마다 서비스 발표와 앞선 24시간 발표 8개, 지점마다 ASOS(작기 시작 ~ 어제)를 새로 받는다. 한 회차 API 호출은 예보 지점 1곳 9~17번 + ASOS 10번으로, 공공데이터포털 하루 한도(개발 계정 1만 번)에 크게 못 미친다.
- **재시도·마감·대체 규칙은 현장 PC와 같다** (cropwater `cropwater_ops.py`). 발표 + 10분부터 0·5·10·15·20·30·45·60·80분에 다시 시도하고 마감은 발표 + 90분. 첫 시도 뒤 앞선 발표를 먼저 받아 대체 발표를 확보한다. 인증·요청 오류(코드 10~12, 20, 21, 30~33, HTTP 401·403)는 바로 멈춘다. 마감 뒤 실행은 한 번만 시도하고 받으면 "지연 수집".
- **회차 결과는 계약의 다섯 가지로 남긴다.** cropwater의 "백업: 직전 발표 (S3)"는 "백업: 직전 발표"로 두고 `rs_method`에 S3를 적는다. 대체 발표의 날마다 일사 방식이 섞이면 S3로 적는다. cropwater의 "다시 만듦"(같은 회차를 다시 실행)은 서버에 받은 기록이 없어 쓰지 않는다.
- **회차 기록(`forecast_runs`)은 예보 지점만 남긴다.** 표의 결과 칸이 예보 기준이라서다. 예보가 없는 지점의 ASOS 조회 결과는 수집 기록(`collect_log.jsonl`)과 요약에 남기고, ASOS가 실패하면 회차 전체를 실패(종료 코드 1)로 알린다. 수집 감시(공3)에서 알림 규칙을 정한다.
- **키는 기록에 남기지 않는다.** 주소·오류 문구·응답 메시지는 모두 `mask_key`를 거친다. 테스트가 결과 파일과 기록에 키가 없는지 확인한다.
- **이번 단계는 DB에 쓰지 않는다.** 결과는 DB 표와 같은 모양의 JSON으로 남기고, 쓰기·업로드 전 검사·원자료 Storage 보관은 물3에서 더한다. `water_outlook`의 `run_id`는 DB가 정하는 번호라서, 지금은 회차 열쇠(`run_at`, `stn_id`, `collector`)를 붙여 두고 물3에서 번호로 바꾼다.
- **시험 실행은 손으로 누를 때만** (`collect-dryrun`). 예약 실행(02:20·17:20)은 물2에서 따로 만든다. 공개 저장소라 Artifacts는 GitHub 로그인 사용자가 받을 수 있지만, 공공 기상 자료와 그 계산 결과뿐이고 키는 들어 있지 않다.

## 알려진 한계
