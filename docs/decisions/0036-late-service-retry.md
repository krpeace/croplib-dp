# 0036. 지연 재실행에서도 서비스 발표 받기를 재시도하고, 회차 전체 재시도 시간에 상한을 둔다 (이슈 #107, 구현 #118)

날짜: 2026-11-15

## 왜 고쳤나
2026-11-12 08:28 KST 늦은 예약 collect 실행(run 43120074440)에서 서귀포(189) 한 곳만 `백업: 직전 발표`가 됐다. 서비스 발표(11/12 02:00) 받기가 `ReadTimeout`(30.31초)이었고, **마감(발표 + 90분) 뒤에 도는 지연 재실행은 서비스 발표를 한 번만 시도**해서(`collect_service`: `now > deadline`이면 `offsets=[None]`) 재시도 없이 앞선 발표(11/11 23:00)로 대체됐다. 정시 회차는 정해진 시각마다 여러 번 시도하므로 같은 일이 생기지 않는다. 결과는 정상 계산이고 `백업: 직전 발표` 표시만 남지만, 백업은 정시 성공이 아니라서 슬롯이 바뀌면 그 지점은 다시 돌지 않는다.
제안은 #107에 있었고, "구현은 NONREP을 켠 뒤 정기 2회차를 본 다음에 정한다"는 조건을 11/14 17:15·11/15 02:15·17:15 정기 회차가 모두 정시·정상으로 채워서 2026-11-15에 계획(#118)을 승인받아 구현했다.

## 결정
1. **지연 재실행의 서비스 발표 재시도:** 마감 뒤에 도는 지점(`out["late"]`)의 서비스 발표 첫 시도가 일시 오류(`status == "retry"`: 시간 초과·서버 오류)이면 **30초 → 90초** 뒤 두 번 더 받는다(`LATE_SERVICE_RETRY_S = (30, 90)`, 한 지점 최대 3시도). `ok`·`partial`·`incomplete`·`nodata`·`fatal`은 다시 받지 않는다(필요한 앞선 발표와 같은 규칙). 시험 실행(`wait=False`)은 마감 뒤여도 그대로 한 번만 받는다. 재시도로 받으면 결과는 `지연 수집`(백업 아님), 끝내 못 받으면 지금처럼 `백업: 직전 발표`.
2. **회차 전체 합계 상한 `RETRY_BUDGET_S = 300`초:** 재시도를 **시작하기 전에** `쓴 시간 + 이번 대기 > 300`이면 그 재시도는 하지 않고 그 지점을 기록한다. `쓴 시간` = 재시도의 대기 + 그 재시도 요청에 걸린 시간(시계 기준). 시작한 재시도는 끝까지 한다. 예산은 회차마다 하나(`SlotResult.retry_budget`)이고 모든 지점이 나눠 쓴다.
3. **상한은 이번에 새로 넣은 재시도만 센다(Q1 결정, 2026-11-15):** 기존 재시도(`NEEDED_ISSUE_RETRY_S`, `ASOS_RETRY_S`)는 **값·동작 모두 그대로**이고 예산에 넣지 않는다. 이미 있는 재시도까지 5분으로 막으면 정시 회차가 달라진다(11/13 17:15 회차는 시간 초과가 15번이라 실패한 시도에 쓴 시간만 약 460초였다).
4. **조용히 넘기지 않는다:** 요약 `단계:` 줄 끝에 `· 지연 재시도 N번 (대기·요청 S초)`, 상한에 걸린 지점이 있으면 별도 줄 `지연 재시도 상한(300초) 도달: M곳은 서비스 발표 재시도를 하지 못함 — 지점 번호`. 재시도를 쓰지 않은 회차(정시 회차 포함)는 문구가 하나도 붙지 않는다. 상한에 걸려도 실행은 실패가 아니고(그 지점 결과는 기존 분류대로 `백업…`), 감시(`monitor`)·`forecast_runs.result` 값 목록(5가지)은 바뀌지 않는다.
5. **정시 회차 동작은 바뀌지 않는다:** 새 코드는 `now > deadline` 분기에서만 돈다(정시 회차의 `offsets` 반복은 그대로). 예산은 기본값 `None`이면 재시도를 하지 않아 직접 `ForecastCollector`를 부르는 기존 시험은 모두 예전 동작이다. 구현 전 코드에서 뽑은 정시 회차 기준값(서비스 발표 첫 시도 시간 초과: 시도 2회·02:15:00 종료·요청 11번, 끝내 시간 초과: 시도 9회·03:30:00·요청 18번)을 시험으로 고정했다.
6. **끄는 법:** `LATE_SERVICE_RETRY_S = ()`로 두면 예전 동작(한 번만 받기)으로 돌아간다(시험으로 확인). 상수는 `collectors/water.py` 한 곳에만 있다.

## 최악 시간 계산
- 시간 초과 한 번 ≈ **34초**(관측 최대 33.84초, 요청 제한 30초 + 처리).
- 한 지점의 새 재시도 최대: 재시도 2번 × 34초 + 대기 30 + 90초 = **188초**(첫 시도 34초는 원래 하던 것).
- 상한이 없다면: 97곳이 모두 3시도 시간 초과면 97 × (3 × 34 + 120) ≈ 21,500초 ≈ **약 6시간**(워크플로 제한 130분이 먼저 끊는다). 이게 #107이 말한 "느린 API 날 회차 시간이 크게 늘 수 있다"의 최악이다.
- **상한 300초:** 재시도를 시작하기 전 `쓴 시간 + 대기 ≤ 300`일 때만 하므로 새 재시도로 늘어나는 시간은 **최대 300 + 34 ≈ 334초(5.6분)**. 이미 있던 첫 시도 시간 초과 비용(97곳 전부 시간 초과면 97 × 34 ≈ 55분)은 이번 변경과 무관하게 그대로.
- 보통의 늦은 재실행: 서비스 발표를 첫 시도에 못 받은 지점이 정시 회차 5회에서 1~6곳(평균 3.4곳)이었으므로 약 3.4 × (30초 + 약 2초) ≈ 110초, 최대 관측 6곳이어도 약 190초 증가 — 상한 안이다.
- 식: `새 재시도로 늘어나는 시간 ≤ 재시도 상한(300초) + 상한을 넘기기 직전에 시작한 마지막 재시도의 요청 시간(약 34초)`.

## 되돌리기·한계
- PR 하나를 되돌리거나 상수를 `()`로 두면 된다. DB 구조·데이터 계약·워크플로·변수 변화가 없다.
- `.github/workflows/collect.yml` 머리 주석의 "마감을 넘기면 한 번만 받아 '지연 수집'으로 남긴다"는 이 결정으로 사실과 달라진다. 워크플로 파일이라 이 PR에서 고치지 않고, 병합 뒤 별도 작은 PR로 고친다.
- 상한 300초·재시도 간격은 늦은 재실행의 실측(요약의 `지연 재시도 N번 (대기·요청 S초)`)을 보고 다시 조정한다.
