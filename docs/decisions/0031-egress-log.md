# 0031. DB에서 내려받은 바이트(egress)를 실행마다 한 줄로 남긴다

날짜: 2026-11-11 (사용자 요청 — S5 egress 추정을 실측으로 바꾸기 위해)

## 배경
Supabase 무료 플랜은 주기(10/23~11/23)마다 egress 5GB 한도가 있다. 11/11 15시 누적 4.73GB(하루 12~14MB, 11/23까지 쓰면 여유 약 100MB)이고, 초과하면 유예 뒤 읽기 전용·402 오류 같은 제한이 걸릴 수 있다. 이 저장소가 DB에서 얼마나 읽는지는 지금까지 추정뿐이었다(S5 계획 `#87` egress 절).

## 결정
1. **Supabase 응답 본문 바이트를 실행(프로세스)마다 합산**한다(`io/egress.py`). 저장 크기가 아니라 **내려받은 JSON 바이트**다. 읽기(`rest_get`)·쓰기 응답(`SupabaseWriter`의 `http_request`, `forecast_runs` 올리기는 `return=representation`으로 줄을 돌려받음)·HEAD(`http_request_h`, 요청 수만)를 센다. GitHub·기상청 응답은 세지 않는다.
2. **한 줄로 남긴다**: `DB 읽기(이 실행): 0.14MB (요청 31번) — forecast_runs 0.09MB · scenarios 0.04MB …`(표별 상위 6개).
   - 수집 실행: 요약(`summary.md`)·알림 요약(`brief.md`)의 `단계:` 줄 아래. 올리기 응답까지 센 뒤에 찍는다.
   - 감시 실행: 출력 마지막 줄(수집 워크플로의 감시 단계와 매시 감시 둘 다).
3. 실행이 아무것도 읽지 않아도 `0.00MB (요청 0번)`을 남긴다(로그에 늘 줄이 있게).
4. 다른 수집기(적산온도·KREI·retention 등)는 같은 함수를 쓰므로 합계는 쌓이지만 줄은 찍지 않는다(필요해지면 한 줄씩 더한다).

## 한계
- **이 저장소의 읽기만** 센다. CropMon 화면(웹)이 읽는 양은 이 저장소에서 알 수 없다. Supabase 대시보드 egress에는 둘이 합쳐 보인다.
- 압축·헤더는 세지 않는다(응답 본문 바이트). Supabase 청구 기준과 소폭 다를 수 있다.
- Storage 다운로드는 `storage` 한 항목으로 센다(retention 등이 쓰는 경우).
