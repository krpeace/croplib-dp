# 0006. 예약 수집 (물2)

날짜: 2026-10-24

## 결정
- **매일 02:20·17:20(KST)에 GitHub Actions로 돈다** (`collect.yml`). 서비스 발표(02시·17시)는 발표 10분 뒤부터 나오므로 그보다 10분 늦게 시작한다. 현장 PC 작업 스케줄러(02:10·17:10)와 겹치지 않는다. cron은 UTC라서 `20 17 * * *`(전날 17:20 UTC = 02:20 KST), `20 8 * * *`로 적는다.
- **늦게 시작해도 괜찮게 한다.** GitHub 예약 실행은 몰리면 늦게 시작한다. 수집기가 마감(발표 + 90분)까지 재시도하므로 30분 늦어도 40분 넘게 기다릴 수 있다. 마감을 넘겨 시작하면 한 번만 받아 "지연 수집"으로 남긴다.
- **실패하면 5분 뒤 한 번 더 돌린다.** 시험 실행에서 공공데이터포털이 몇 분 동안 모든 요청에 응답하지 않은 적이 두 번 있었다. 같은 회차를 다시 계산해 덮어쓴다(결정 0005). 회차 기록도 다시 실행한 결과로 바뀐다.
- **회차는 시작할 때 한 번 정한다.** 다시 실행할 때 회차가 바뀌지 않게 하려는 것이다.
- **60일 자동 중지를 막는다** (`keepalive.yml`). GitHub는 공개 저장소에 60일 동안 활동이 없으면 예약 실행을 멈춘다. 매달 1일 예약 실행 두 개를 API로 다시 켠다. 기본 토큰(`actions: write`)만 쓰고 커밋은 만들지 않는다.
- **알림:** 두 번 모두 실패하면 실행이 실패로 끝나 GitHub 실패 메일이 간다. 회차 기록에도 "실패"와 이유가 남는다. 우리 쪽 알림 메일과 13시간 무갱신 알림은 공3에서 만든다.

## 확인
- 합친 뒤 첫 예약 실행(02:20)의 알림 요약으로 "정시 성공"과 DB 올리기를 확인한다.

## 고침 (2026-10-25)
- 첫 예약 실행(10/25 02:20 예약)이 **04:29에 시작**했다(2시간 9분 지연, 마감 지나 "지연 수집"). 2시간마다 걸어 둔 감시도 한 번 건너뛰었다. GitHub는 예약 실행이 몰리면 늦추거나 건너뛸 수 있다고 안내한다.
- **회차마다 세 번 건다** (02:15·02:35·02:55, 17:15·17:35·17:55). 각 실행은 DB를 보고 그 회차가 이미 "정시 성공"이면 바로 끝낸다(`--skip-if-done`). 지연·백업·실패면 다시 돌아 결과를 낫게 한다. 같은 `concurrency` 묶음이라 동시에 돌지 않는다.
- 감시는 매시 40분으로 바꿨다(정각을 피하고 빈틈을 줄임).
- 이래도 정시를 못 맞추면, 지연이 거의 없는 "호출 방식"(workflow_dispatch)을 바깥 예약(Supabase pg_cron 등)에서 부르는 방법으로 넘어간다. 그때는 이 저장소 실행 권한만 가진 GitHub 토큰이 필요하다.
