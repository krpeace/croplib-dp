# 0007. 수집 감시는 GitHub 이슈로 알린다 (공3)

날짜: 2026-10-24

## 결정
- **알림 창구는 GitHub 이슈다.** 저장소 주인에게는 이슈가 열리거나 댓글이 달리면 GitHub가 메일을 보낸다. 메일 서버나 발송 서비스 키를 새로 두지 않아도 되고, 알림 이력이 저장소에 남는다(2026-10-24 사용자 승인). 다른 주소(회사 메일 등)로도 받아야 하면 그때 메일 발송 서비스를 붙인다.
- **경고 규칙** (`core/monitor.py`, 서버 회차 기록 `collector = actions`만 본다)
  - 오류: 마지막 회차가 끝난 지 13시간 넘음(화면 "마지막 갱신"의 멈춤 기준과 같음), 마지막 회차 결과가 실패
  - 경고: 마지막 회차가 지연 수집·백업(직전 발표, S3) — H3 정시 수집률에 영향을 주는 일, 18시(17:20 회차 + 여유) 뒤에도 어제 ASOS 관측이 DB에 없음
  - 마지막 회차만 본다. 앞 회차가 실패했어도 다음 회차가 정상이면 회복으로 본다.
- **같은 경고로 메일이 쌓이지 않게** 이슈 본문에 지금 경고들의 열쇠를 숨겨 두고, 새 열쇠가 생길 때만 댓글을 단다. 본문은 매번 최신 점검 결과로 바꾼다. 경고가 모두 사라지면 "정상 회복" 댓글을 달고 닫는다. 다시 생기면 새 이슈를 연다.
- **언제 보나:** 예약 수집이 끝날 때(결과를 바로 알림)와 2시간마다(`monitor.yml`, 수집 자체가 안 돈 경우를 잡음). 감시가 실패해도 수집 결과는 바뀌지 않는다(수집 실행에서는 감시 단계 실패를 무시).
- 감시 실행도 60일 자동 중지 대비(`keepalive.yml`)에 넣었다.

## 보충 (2026-10-28, 이슈 #33)
- **수집하는 지점만 본다.** 관측·적산온도 마지막 날은 `stations.has_forecast = true`인 지점만 읽는다(지금 대표 10곳). 지점 사전이 105곳으로 늘면서(CropMon#38) 원래 수집하지 않는 95곳까지 "어제 관측 없음"으로 잡는 가짜 경고(#32)가 났기 때문이다. 수집 여부를 정하는 열은 `has_forecast` 하나로 맞추고 `is_active`·`is_representative`는 쓰지 않는다.
- 전 지점으로 넓힐 때(#28)는 그 지점의 `has_forecast`만 켜면 감시가 자동으로 따라간다. 경고 규칙(13시간 멈춤·실패·지연·18시 뒤 관측·12시 뒤 적산온도)은 바꾸지 않았다.
- 감시는 지금 매시 40분에 돈다(위 "2시간마다"는 처음 결정 당시 값).

## 보충 (2026-10-29, 결정 0017)
- **적산온도 감시 대상은 운영 지점(`is_active = true`, 지금 97곳)이다.** 적산온도·적산일사를 전 지점 공개하기로 해서(수집 대상과 맞춤), 관측(`asos`)과 달리 `has_forecast`가 아니라 `is_active`로 본다. 관측 감시는 그대로 `has_forecast` 지점만 본다.
- 적산온도는 지점마다 묻지 않고 한 번에 묻는다: `heat_daily`에서 어제·작물 공통(`crop_id = common`)·`gdd_cum`이 있는 지점 목록을 받아 운영 지점과 비교. 매시간 호출 수가 지점 수와 상관없다.
- 빠진 지점이 10곳을 넘으면 "N곳 — 앞 10곳 …"으로 줄인다.
- **수집 지점 0곳이면 오류**("수집 지점이 0곳 — 지점 사전 has_forecast 확인", `error:stale`급). 전에는 0곳이면 관측 경고가 조용히 사라졌다. 적산온도 대상(`is_active`)이 0곳일 때도 오류.

## 보충 (2026-10-30, 이슈 #37)
- **"갱신 멈춤" 기준을 13시간 → 17시간으로 늘렸다.** 본문의 "13시간"은 처음 결정 당시 값이다.
- 물 회차는 02시·17시 두 번이라 02시 회차가 02:30쯤 끝나면 17시 회차가 끝나는 17:30쯤까지 15시간이 빈다. 13시간 기준이면 아무 문제가 없어도 매일 15:30~17:30에 "갱신 멈춤" 오류 이슈가 열렸다(10/29 #35: 02:29에 끝난 회차 → 15:40 감시에서 13.2시간 → 오류 → 17:28 회복). CropMon 화면의 "마지막 갱신"도 같은 기준이라 같은 일이 보인다.
- 정상일 때 가장 긴 간격은 02시 회차가 02:15쯤 일찍 끝나고 17시 회차가 마감(발표 + 90분)인 18:30에 끝나는 약 16.3시간이다. 여유를 두어 17시간. 진짜 멈춤도 잡는다: 17시 회차가 빠지면 다음 날 19:30쯤, 02시 회차가 빠지면 다음 날 10:30쯤 오류.
- 값은 CropMon `src/domain/freshness.ts`의 `STALE_AFTER_MS`와 같아야 한다(CropMon 짝 PR). 다른 경고 규칙은 바꾸지 않았다.

## 알아 둘 것
- 경고 단계(지연·백업)도 메일이 간다. 서비스는 계속되지만 H3 정시 수집률 판단에 필요한 기록이라서다. 너무 잦으면 경고는 이슈 본문에만 남기고 댓글은 오류만 달도록 바꾼다.
